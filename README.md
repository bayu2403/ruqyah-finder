# Taut Ruqyah (ruqyah-finder)

Web app connecting people who believe they need ruqyah syari with nearby
**verified** ruqyah practitioners (ustad), via WhatsApp. Target region:
Indonesia. Not a medical or religious authority — just a matchmaker, with
verification as the main quality gate.

## Status

**Static mockup** for demoing the flow to a partner organisation. No database
and no login: ustadz data is hardcoded, and requests are stored in the
browser's `localStorage`, so a request submitted in one tab shows up live in
the ustadz and admin pages in another tab of the same browser. Everything
that needs a real backend is marked `TODO(BE)` in the code and listed in
[`docs/BACKEND-TODO.md`](docs/BACKEND-TODO.md).

## Pages

| Route | Who | What |
|---|---|---|
| `/` | Public | Landing page and request flow: GPS or region dropdown → map with the 5 nearest verified ustadz (approximate areas only) → name, WhatsApp, service, preference → submit to the pool |
| `/ustadz/` | Ustadz | Pool of nearby waiting requests. "Ambil" claims one (it disappears for everyone else) and only then reveals the user's name and number, with a pre-filled WhatsApp link |
| `/admin/` | Organisation admin | Request overview, manual assignment of requests nobody took within 6 hours, verify/activate/add ustadz, reset demo data |
| `/edukasi/` | Public | How to recognise ruqyah syar'i vs. practices that misuse the name |
| `/ruqyah-mandiri/` | Public | Self-ruqyah guide: Al-Fatihah, Ayat Kursi, end of Al-Baqarah, the three Quls, two du'a |

## How matching works

1. The user's location comes from GPS or the provinsi → kabupaten/kota →
   kecamatan dropdown.
2. The map shows up to 5 available ustadz (verified, active, accepting new
   requests) within 50 km, each at an approximate location offset by
   0.6–1.2 km, never their real address.
3. A submitted request enters the pool. An ustadz sees it if their gender
   matches the user's preference, they offer the requested service, and
   they're within 15 km (50 km once the request is 2 hours old; any distance
   for online consultations).
4. The first ustadz to tap "Ambil" gets it and messages the user on
   WhatsApp. The conversation continues there.
5. Requests still waiting after 6 hours are flagged for the admin to assign.

The rules live in `lib/matching.ts`.

## Structure

- `app/` — routes listed above (Next.js 14 App Router, static export)
- `components/request/` — the request flow; `components/map/` — Leaflet map
- `components/ustadz/`, `components/admin/` — the two dashboards
- `lib/data/` — hardcoded ustadz and region lists
- `lib/store.ts` — mock database (`localStorage`); each function maps to a
  future Supabase call
- `lib/content/ayat-ruqyah.ts` — Qur'an verses, generated by
  `scripts/gen-ayat.py` (QuranEnc Uthmani text, Kemenag translation,
  CC BY-SA 4.0)
- `docs/` — product design (`DESIGN.md`), target schema
  (`schema-final.sql`), backend migration list (`BACKEND-TODO.md`)
- `legacy/prototype-html/` — original single-file prototype, kept for
  reference

## Quick start

```bash
npm install
npm run dev
```

Open <http://localhost:3000>. To demo the full flow, submit a request on
`/`, then open `/ustadz/` (pick "Ustadz Ahmad Fauzi" for Jakarta Selatan)
and `/admin/` in other tabs. "Reset data demo" at the bottom of `/admin/`
restores the sample data.

`npm run build` produces the static site in `out/`, which the GitHub Pages
workflow deploys.

## Where the product thinking lives

`docs/DESIGN.md` is the real source of truth for where this is headed: a
pre-screening questionnaire (to route medical red flags to professional
help *before* anything ruqyah-related), a `laporan` (report/flag) mechanism
for ongoing ustad quality control, and post-case follow-up — none of which
is implemented in the current app code yet.
